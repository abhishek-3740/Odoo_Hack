# Supabase Backend — Zito_BC Hackathon

Local Supabase stack running entirely in Docker. **Status: verified working** — see
[Verification](#verification) for what was actually tested.

## Quick Start

```bash
# 0. Docker Desktop must be running first (whale icon in taskbar, not animating)
npx supabase start     # start all services
npx supabase status    # show URLs + keys
npx supabase stop      # stop (keeps data)
npx supabase db reset  # wipe DB, re-apply all migrations + seed
```

All credentials are already in `.env` (gitignored).

## Gotchas (learned the hard way)

### 1. `apikey` header must match `Authorization`
The **`apikey` header determines your role** (anon vs service_role). If you send the secret
key in `Authorization` but the publishable key in `apikey`, you silently get downgraded to
anonymous: admin endpoints return `403 not_admin`, and RLS gets applied even though you
expected a bypass.

```js
// WRONG — role comes from apikey, so this is an anon request
{ apikey: PUBLISHABLE, Authorization: `Bearer ${SECRET}` }

// RIGHT
{ apikey: SECRET, Authorization: `Bearer ${SECRET}` }
```

### 2. `supabase_vector` container restart-loops on Windows
Log shipper can't reach the Docker daemon over `tcp://localhost:2375` (Docker Desktop doesn't
expose it by default on Windows). **Harmless** — only breaks the Analytics log viewer.
Database, auth, REST, storage and realtime are unaffected. To fix: Docker Desktop →
Settings → General → enable "Expose daemon on tcp://localhost:2375 without TLS".

### 3. Keys change if you recreate the stack
`npx supabase stop` then `start` keeps them. `supabase db reset` keeps them. But if you ever
delete the containers/volumes, rerun `npx supabase status` and update `.env`.

## Adding a table

```bash
npx supabase migration new my_table
# edit supabase/migrations/<timestamp>_my_table.sql
npx supabase db reset   # apply + seed
```

Remember to `alter table ... enable row level security;` — without RLS enabled, every
table is fully readable by anyone with the publishable key.
